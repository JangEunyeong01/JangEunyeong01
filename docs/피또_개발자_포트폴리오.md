# 피또 (Fitto) — 개발자 포트폴리오

> 개인 프로젝트 · 1인 개발 · React Native (Expo)
> **작성 중 문서입니다.** 개발과 병행해 채워나가며, `⬜` 표시 항목은 해당 기능이 구현되면 작성합니다.

---

## 1. 이 프로젝트를 만든 이유

⬜ *직접 작성 — 아래 뼈대만 잡아둠*

- 개인적인 음식 알러지 경험에서 출발, 가족을 위해 만들기 시작한 앱
- 이름 "피또" = Fit(어울리다 / 건강하다) + 또(나한테 또 맞다 / 또 건강해지자)
- 물방울 마스코트: 물을 인간 건강의 핵심 요소로 보고 이를 캐릭터화한 '건강 지킴이' 컨셉 — 사용자 리서치가 아니라 본인의 기획 판단에서 나온 컨셉이라는 점을 명시

**이 문서에서 증명하려는 것**

| 축 | 피또에서 보여줄 근거 |
|---|---|
| 디자인 → 개발 연결 | 디자인 핸드오프 문서의 값을 코드 토큰으로 이식하고, 그 출처를 코드에 남긴 구조 |
| 인터랙션 구현력 | 제스처 기반 입력, 상태에 반응하는 캐릭터 애니메이션 |
| 구조 설계·품질 | 상태 스키마 버전 마이그레이션, 목데이터와 실데이터의 경계 분리 |
| 1인 개발자의 스코프 판단 | 플랫폼 제약을 우회하되 기술 부채를 명시하고 교체 시점을 예고한 결정들 |

> 두리(팀 프로젝트)에서 다루는 협업·API 연동·리드 경험과 겹치지 않도록, 이 문서는 **혼자 설계한 구조**와 **디자인-코드 연결**에 초점을 둡니다.

## 2. 기술 스택과 전환 결정

**현재 스택** — Expo 57 / React Native 0.86 / TypeScript / Zustand(persist) / React Navigation 7 / Reanimated 4 + Gesture Handler / react-native-svg

⬜ *직접 작성이 필요한 부분:* 초기에 Next.js 기반 웹으로 시작했다가 Expo(React Native)로 전환한 이유.

전환 자체가 좋은 포트폴리오 소재입니다. 다음 질문에 답하는 방식으로 쓰면 됩니다.

- 웹으로 만들었을 때 무엇이 걸렸는가 (건강 관리 앱의 사용 맥락 — 하루에 여러 번, 짧게, 손에 들고)
- 전환하면서 무엇을 버리고 무엇을 가져왔는가 (디자인 핸드오프 문서는 살아남음 → 3장으로 연결)
- 전환 비용을 감수할 만하다고 판단한 근거

`AGENTS.md`에 *"Expo HAS CHANGED — 버전 문서를 먼저 읽을 것"*을 규칙으로 걸어둔 것도, 버전 차이로 인한 오작동을 미리 막으려 한 판단으로 언급할 수 있습니다.

## 3. 디자인 → 코드: 핸드오프 값을 옮기는 규칙

**작성 가능 — 근거 확보됨**

디자인 산출물(`design-source/design_handoff_fitto/README.md`)의 값을 코드로 옮기면서, **옮겼다는 사실과 출처를 코드에 남기는 규칙**을 세웠습니다.

- `src/theme/tokens.ts` 첫 줄: *"design-source README 값 그대로 이식"*
- `src/utils/goals.ts` 첫 줄: *"README '온보딩 — 목표 계산식'을 그대로 옮긴 것. 수치를 임의로 바꾸지 않는다"*
- 개별 토큰에도 출처 주석 — 예: `periodBadgeGradient`에 *"README: lavender .9 → peach .75"*
- README에 값이 없어 **직접 판단한 부분은 그렇다고 명시** — 예: `overlay.sheetBackdrop`에 *"README에 값이 없어 튜토리얼 딤과 같은 색을 옅게 썼다"*

**왜 이렇게 했는가 (여기가 핵심)**
⬜ *직접 작성* — 디자인과 구현이 어긋났을 때 무엇이 맞는지 되짚을 수 있어야 한다는 문제의식을 본인 언어로. 두리에서 문서와 앱의 색 토큰을 일치시킨 경험과 연결하면 일관된 서사가 됩니다.

**파생 값은 계산해서 쓴다**
`alpha()` 헬퍼로 원본 토큰에서 투명도를 계산 — 반투명 색을 별도 상수로 박아두지 않아, 브랜드 색이 바뀌면 파생 색이 함께 따라옵니다.

## 4. 기획 → 코드 구조: 캐릭터 성격 3종이 문구 테이블이 되기까지

**작성 가능 — 근거 확보됨**

마스코트의 성격 3종(친근형 / 엄격형 / 중립형)이라는 기획을, 화면 곳곳에 흩어진 문구가 아니라 **하나의 문구 리소스 테이블**로 구현했습니다.

- `src/copy/persona.ts` — 8개 상황 × 3개 성격의 문구를 함수 테이블로 관리
- 규칙: *"하드코딩 카피 대신 이 테이블을 통해서만 참조한다"*
- 값이 들어가는 문구는 함수로 — `(v: { remainKcal }) => ...` 형태라 성격별로 **문장 구조 자체가 다를 수 있음** (친근형은 물 기준, 엄격형은 칼로리 기준으로 말하는 식)

⬜ *덧붙일 것:* 성격에 따라 같은 상황에서 무엇을 먼저 말하는지가 달라진다는 점 — 단순 말투 치환이 아니라 **정보 우선순위 설계**였다는 관점으로 정리하면 기획자로서의 판단이 드러납니다.

## 5. 상태 설계와 스키마 마이그레이션

**작성 가능 — 근거 확보됨**

`src/store/useAppStore.ts` — Zustand + AsyncStorage 영속화. 기기에 저장된 상태가 앱 업데이트 이후에도 깨지지 않도록 **버전 마이그레이션**을 두었습니다.

- `version: 2`, `migrate` 함수로 버전별 이관 처리
- v2 이관 내용: 홈 카드 기본 순서가 'A 스택'에서 'B 히어로'로 바뀌었을 때, **사용자가 순서를 직접 바꾼 적이 없을 때만**(= 이전 기본값 그대로일 때만) 새 순서로 옮김
- 이유 주석: *"이미 저장된 상태에는 기본값 변경이 자동 반영되지 않아 버전별로 옮겨준다"*

이 판단이 왜 필요했는지가 포인트입니다 — 기본값을 바꾼다는 것은 **이미 그 값을 쓰고 있는 사용자가 있다**는 뜻이고, 그 사람이 직접 설정한 순서를 덮어쓰면 안 된다는 것.

⬜ *덧붙일 것:* 날짜별 기록(`dailyRecords`)을 날짜 키 맵으로 잡은 이유, `getRecord`가 없는 날짜에 빈 레코드를 반환하도록 한 이유(호출부마다 null 체크를 하지 않게).

## 6. 인터랙션 구현

**작성 가능 — GIF 녹화 필요**

**물 섭취 카드 — 제스처 입력** (`src/screens/home/cards/WaterCard.tsx`)
- 세로 드래그로 증감. 위로 끌면 증가, 아래로 끌면 감소
- 약 4px당 50ml, **50ml 단위로 스냅** — 손가락 움직임이 정확할 수 없다는 전제
- Gesture Handler의 worklet에서 계산하고 `runOnJS`로 상태 반영
- 탭(컵), 버튼(+250ml), 되돌리기까지 **같은 동작에 세 가지 진입로** 제공

**캐릭터가 물 섭취량에 반응** (`src/components/FittoCharacter.tsx`, `src/utils/health.ts`)
- 섭취량/목표 비율을 5단계로 나눔 (바싹 마름 / 목마름 / 보통 / 촉촉 / 완전 만족)
- 단계별로 크기(0.9 → 1.06)와 **부유 애니메이션 주기**가 달라짐 — 0단계는 아예 멈추고, 4단계는 3.2초 주기로 가장 활발하게
- 즉, "물을 안 마시면 캐릭터가 축 처진다"가 색뿐 아니라 **움직임의 속도**로 표현됨

⬜ **녹화할 것:** ① 물컵 드래그 증감 ② 단계 변화에 따른 캐릭터 반응 (0단계 → 4단계 연속으로) ③ 온보딩 진행 흐름

## 7. 플랫폼 제약과 우회 — 그리고 기술 부채를 남기는 방식

**작성 가능 — 근거 확보됨**

원본 웹 프로토타입은 캐릭터의 5단계 상태를 CSS `filter`(grayscale / saturate / brightness)로 표현했지만, **React Native의 `Image`에는 CSS filter를 적용할 수 없습니다.**

선택한 해법 — 반투명 오버레이 3겹으로 근사:
- 채도 감소 → 회색 레이어의 불투명도로 (`grayscale * 0.55`)
- 채도 증가 → 브랜드 블루 레이어로 (`(saturate - 1) * 0.28`)
- 밝기 → 흰색 레이어로 (`(brightness - 1) * 0.5`)

**중요한 건 그 다음입니다.** 코드에 이렇게 남겼습니다 — *"최종 5단계 일러스트가 준비되면 이미지 스왑으로 교체 권장"*, 그리고 오버레이 색 토큰에도 *"이미지 스왑으로 바뀌면서 함께 제거된다"*.

⬜ *덧붙일 것:* 근사치로 가되 **더 나은 해법과 교체 조건을 명시**한 이유. 1인 개발에서 지금 할 일과 나중에 할 일을 가르는 기준을 어떻게 잡았는지.

같은 맥락의 다른 사례:
- 반폭 카드에서 원본의 가로 배치(컵+컨트롤)가 45px로 찌그러져 세로 배치로 변경 — 원본을 따르지 않기로 한 판단과 그 이유를 주석으로 (`WaterCard.tsx`)
- 웹에서 `absoluteFill`에 width/height가 없어 이미지가 원본 크기(578×731)로 삐져나오는 문제를 크기 명시로 해결 (`FittoCharacter.tsx`)

## 8. 트러블슈팅

**1건 작성 가능 — 개발하며 추가**

### 온보딩 태그를 빠르게 두 번 누르면 앞선 선택이 사라지는 문제

- **증상:** 태그 선택 화면에서 두 개를 빠르게 연속으로 누르면 먼저 누른 것이 선택 해제됨
- **원인:** 선택 배열 전체를 인자로 받아 갱신하는 구조라, 리렌더 전에 두 번째 클릭이 들어오면 **갱신 전의 낡은 배열**을 기준으로 덮어씀
- **해결:** `toggleObTag(key, value)` — 배열이 아니라 **바뀐 항목 하나만** 받고, 스토어 내부에서 항상 최신 상태를 기준으로 토글
- **코드:** `src/store/useAppStore.ts`

> ⬜ 개발하면서 겪는 문제를 이 형식(증상 → 원인 → 해결 → 파일)으로 계속 추가. **원인 분석이 한 줄이라도 있어야 기록의 값이 생깁니다.**

## 9. 프론트 우선 구현과 데이터 경계 설계

**작성 가능 — 근거 확보됨**

이 프로젝트는 화면과 인터랙션을 먼저 완성하는 순서로 진행했습니다. 그래서 데이터는 아직 목데이터지만, **연동 지점을 처음부터 한 곳씩 격리해두고 각각이 어떤 소스로 교체될지 코드에 명시**했습니다.

| 위치 | 현재 | 교체 대상 |
|---|---|---|
| `useAppStore.seedMockToday` | 홈 화면 예시 기록 | 사용자 실제 입력 + 건강 API |
| `screens/home/mockData.ts` | 지난 6일 걸음 수 | 건강 API |
| `HealthScreen`의 `sittingHours` | 고정값 6.5h | 기기 센서 |
| `data/foods.ts` | 로컬 음식 목록 | 음식 영양성분 API |
| `utils/periodMock.ts` | 생성된 주기 데이터 | 사용자 입력 기록 |

각 지점에 *"실제 데이터 소스 연동 전까지"*, *"기기 센서 연동 전 예시값"* 형태로 주석을 달아, 연동 시 무엇을 건드려야 하는지가 코드에서 바로 보이게 했습니다. UI 컴포넌트는 데이터의 출처를 모르고 형태만 알기 때문에, 소스가 바뀌어도 화면 코드는 그대로입니다.

⬜ *덧붙일 것:* 화면을 먼저 완성하는 순서로 간 이유. 그리고 그 순서를 택했을 때 **데이터 경계를 미리 그어두지 않으면 나중에 무엇이 문제가 되는지** — 여기가 이 장의 핵심입니다.

## 10. 테스트와 품질 *(선택 — 넣을지 나중에 판단)*

⬜ 계산 로직에 테스트를 붙인다면 이 장이 생깁니다. 지금 당장 필요한 건 아니고, **화면 구현이 일단락된 뒤**에 판단하면 됩니다.

붙인다면 대상은 이미 순수 함수로 분리되어 있습니다.

- `utils/goals.ts` — Mifflin-St Jeor 기초대사량, 활동계수, 목표별 보정, 하한 1200kcal, 체중 기반 물 목표(50ml 단위 반올림)
- `utils/health.ts` — 물 5단계 구간 계산, 칼로리 5개 상태 구간(부족/양호/목표 달성/주의/초과)
- `utils/periodMock.ts` — 연·월 인덱스 변환

경계값(0, 목표 초과, 입력 누락 시 기본값)이 명확해서 테스트 케이스가 바로 나옵니다.
